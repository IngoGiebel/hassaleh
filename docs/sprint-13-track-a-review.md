## 1. Scope

Reviewed Track A deliverables on branch `trunk`:

- `src/hassaleh/runtime/core.py` (handler registry + dispatch loop, 115 lines)
- `src/hassaleh/runtime/types.py` (`Intent`, `Result`, `Principal`, `Ctx`, 57 lines)
- `tests/test_runtime_core.py` (8 unit cases, 199 lines)

Out of scope per plan: Cypher handler bodies (Track B), capability scope catalogue + schema constraint (Track C), observability emitters (Track D), live-Neo4j integration tests (Track E), end-to-end demo (Track F). I limit findings to Track A's surface — the dispatch skeleton, the value types, and the invariants those impose on the downstream tracks.

Track A is structurally sound: the canonical execution order matches §2.5, the registry is the only path to a handler, capability is read from registration (I-CR-3), and unknown / unauthorized intents short-circuit before any session is opened. Findings below concern the *invariants* the dispatch loop is supposed to enforce — three of which are not enforced by the code as committed.

## 2. Security findings (Blocking)

- **`Principal.scopes` is a mutable `list` on a frozen dataclass — post-construction mutation defeats capability check.** `types.py:47` declares `scopes: list[str] = field(default_factory=list)` on `@dataclass(frozen=True) Principal`. `frozen=True` only blocks attribute *reassignment*; the underlying list remains mutable. Any code holding a `Principal` reference can call `principal.scopes.append("market.reviewer.write")` *after* the runtime has authenticated the caller, and the next `execute()` will see the elevated scope set. The capability check at `core.py:75` is `required_capability in ctx.principal.scopes` — it trusts whatever the list contains at call time. This is a concrete auth-bypass primitive, not a theoretical concern: any future Track-D log enricher, Track-E test fixture, or Track-F adapter that takes a `Principal` and *thinks* it can't escalate scopes can in fact do so. Fix: type as `tuple[str, ...]` (default `()`) or `frozenset[str]` (default `frozenset()`); both are immutable and `in` works on both.

- **`_REGISTRY` is exported in `core.py::__all__`.** `core.py:110` includes the underscore-prefixed `_REGISTRY` in the public surface. The convention "`_name` means private" plus the explicit `__all__` listing means downstream importers (and code-completion) will treat it as an intentional API. The test fixture `_reset_registry` (`tests/test_runtime_core.py:35-40`) needs mutable access for isolation — that is a *test-only* affordance and should not bleed into the public surface. Today this enables a Track-B handler module to legitimately call `_REGISTRY.clear()` and silently un-register every other handler (turning every previously-registered intent into `validation-error / unknown-intent-type`). Fix: drop `_REGISTRY` from `__all__`, expose a narrowly-scoped `_reset_registry_for_tests()` helper used by the autouse fixture, or move to a per-runtime registry (see §3).

- **`Result.error_message` propagates exception class name + repr to the caller.** `core.py:94` builds the message as `f"{type(exc).__name__}: {exc}"`. The implementation log §"Open items" item 2 acknowledges this and defers redaction to "Track D at log-emit time" — but Track D redacts *logs*, not return values. The `Result` flows back to the caller. Today the caller is internal (Market Pipeline workers); the moment Track E or any future adapter exposes `execute()` over IPC/HTTP, this leaks: Cypher syntax errors carry query fragments, `IntegrityError`-style exceptions carry constraint names and (via Neo4j 5 driver behaviour) sometimes parameter values, OS errors carry filesystem paths, and any exception subclass name reveals which library threw. Fix in Track A: return a generic `error_message="internal handler error"` and put the full `f"{type(exc).__name__}: {exc}"` only into the *internal* log/span (Track D's job). Mark this as a Track-A precondition for any non-internal surface so Track E doesn't have to relitigate it.

## 3. API / interface findings

- **`Handler` and `SessionFactory` use `Any` for tx and session.** `core.py:25-26`. The plan §2.1 promises a typed handler signature `def handle(intent: T, tx: Transaction, ctx: Ctx) -> Result`. Track A leaves both `tx` and the session as `Any`, which means Track B handlers cannot rely on a Protocol for `tx.run(...)` shape, and the test fixture (`tests/test_runtime_core.py:43-55`) silently accepts a `MagicMock`. A `typing.Protocol` for `Tx` with `run`, and one for `Session` with `begin_transaction`, would close the loop — and would have caught the silent typo a future test will introduce. Non-blocking, but it is the difference between the value types being type-checked end-to-end and being a string-typed core in the middle of an otherwise frozen-dataclass module.

- **`HassalehRuntime` does not own its registry.** `core.py:49-60`. The runtime resolves intents against the *module-level* `_REGISTRY` rather than against an instance attribute. This is consistent with plan §2.3 ("module-level decorator registry") so I am not blocking on it, but it forecloses three useful properties: (a) parallel test runs can't construct two runtimes with disjoint handler sets; (b) two services in one process (e.g. a future "shadow" runtime for replay) can't coexist; (c) the `_reset_registry` autouse fixture is the only thing keeping tests isolated — accidentally-imported Track-B handlers at collection time get clobbered. If §2.3 is to remain authoritative this is acceptable, but consider taking `registry: Registry | None = None` on `__init__` and defaulting to the module singleton — costs nothing and unlocks the seam.

- **`register_handler` accepts an empty `requires_capability`.** No validation on the `requires_capability` parameter. An empty string is a legal registration; the only thing that would catch a typo or a missing capability annotation is the capability-check failing at runtime. Plan §2.5 implies a non-empty grant; enforcing `requires_capability.strip()` non-empty at registration time fails fast at import. Minor, non-blocking.

- **`ResultKind` literals are untyped at construction.** `Result(kind="ok", ...)` is fine for the literal `"ok"`, but `kind="precondition-failure"` (typo) would type-check under most checkers depending on inference. The handler tests (test 6, `tests/test_runtime_core.py:158-163`) pass typed literals correctly, but a future handler returning a misspelled kind would silently flow through to the metrics layer (Track D) as an unknown label. Fix: a tiny `Result.ok(...)` / `Result.precondition_failed(...)` factory layer in Track B, or `assert result.kind in get_args(ResultKind)` in `execute()`. Non-blocking for Track A — but Track D needs the discipline.

## 4. Precondition semantics (Blocking)

- **§2.4 violation — `ctx.now` is NOT runtime-bound; the caller supplies it.** Plan §2.4 is unambiguous: *"`$now` in handler Cypher is the runtime's monotonic UTC timestamp taken at transaction-open time and bound via `ctx.now` on the handler context. Handlers MUST NOT invoke `datetime.now()` directly — the runtime owns time for determinism and testability."* The implementation log §"Plan-review compliance" claims `Ctx.now` is set by the runtime, citing the docstring on `types.py::Ctx`. **The docstring is aspirational; the code does not implement it.** `core.py::execute` (`core.py:62-87`) accepts `ctx: Ctx` from the caller, never inspects or replaces `ctx.now`, and passes the caller-supplied `Ctx` straight to the handler. A caller can pass `Ctx(principal=..., now=datetime(1970, 1, 1, tzinfo=timezone.utc))` and every `$now` binding inside the handler's Cypher (per the §3.1 mutation) will write 1970 into `analystAt`, `verdictAt`, etc. Two consequences: (1) determinism for tests and replay is left to the caller's discipline, which is exactly what §2.4 says it must not be; (2) ordering invariants on the `Attempt` timeline (analystAt < reviewAt) become falsifiable by any caller. Fix: have `execute()` build a fresh `Ctx` from a `Principal` argument plus a runtime-bound `now = datetime.now(timezone.utc)` taken *immediately after* `tx = session.begin_transaction()` and *before* the `handler(...)` call — that's where §2.4 places the boundary. The current `Ctx` shape is fine; what changes is whose hand fills the `now` field.

- **"The runtime never re-raises" is not true for commit/rollback/session-open failures.** The implementation log claims this invariant explicitly. The `try/except Exception` block at `core.py:86-95` covers only the handler body. The subsequent `tx.commit()` (`core.py:99`), the `tx.rollback()` on the non-`ok` branch (`core.py:101`), the `tx.rollback()` *inside* the except (`core.py:89` — itself can raise), the `session.begin_transaction()` (`core.py:85`), and the `self._session_factory()` context-manager `__enter__`/`__exit__` are all outside any catch. A network blip during commit, a connection-pool exhaustion at session open, or a rollback-on-rollback (driver in a bad state) all escape `execute()` as raw exceptions — directly contradicting the §2.4 invariant *"Exception escaping the handler is caught […] and returned as `Result(kind=internal-error, error_code=handler-exception, ...)`. The runtime never re-raises."* Fix: wrap the entire `with self._session_factory()` block in an outer `try/except`, returning `internal-error` with a distinguishable `error_code` (e.g. `commit-failed`, `session-open-failed`) so Track D can label the metric correctly. Two distinct error codes are warranted because the *meaning* differs — handler bug vs. infrastructure transient — and the retry policy a downstream caller chooses will differ accordingly.

- **`tx.rollback()` swallowing on the exception path.** Even if Track A keeps the current narrow try/except, the `tx.rollback()` at `core.py:89` should itself be wrapped — a rollback exception masks the original handler exception in the returned `error_message`, and worse, leaks out as the new top-level exception. Either suppress and log (Track D) or chain via `from exc`. Non-blocking on its own but inseparable from the previous fix.

- **No verification that the handler receives the same `tx` that gets committed.** `core.py:84-99`: `tx = session.begin_transaction()` then `handler(intent, tx, ctx)` then `tx.commit()`. The single-tx invariant of §2.4 is structurally upheld here, but there is no guard against a future refactor introducing a second `begin_transaction()` call (e.g., a "for retries" loop). A single defensive assertion or a comment block tied to §2.4 would harden the invariant against drift. Non-blocking.

## 5. Test coverage observations

- **No test enforces §2.4 runtime-bound `now`.** The reason the §2.4 violation in §4 above slipped through is that `tests/test_runtime_core.py` constructs `Ctx` with a fixed test timestamp (`_ctx()` at line 58-62) and never asserts that the runtime overrides it. A test of the form *"caller passes `now=epoch_zero`; handler-observed `ctx.now` is within ε of wall-clock"* would fail today and is the right gating test for the fix.
- **No test for the commit/rollback exception path.** The §4 finding ("runtime never re-raises") has no test. Cases worth adding: (a) `tx.commit()` raises → returns `internal-error / commit-failed`, no exception escapes; (b) `tx.rollback()` on the non-ok branch raises → returns the original `Result`, no exception escapes; (c) `session_factory()` raises → returns `internal-error / session-open-failed`.
- **No test for `Principal.scopes` immutability.** Add `with pytest.raises(Exception): principal.scopes.append("x")` — this test will *fail* under the current `list[str]` typing (lists are mutable) and *pass* under the recommended `tuple[str, ...]` / `frozenset[str]` fix. That's the test that distinguishes "I documented immutability" from "I implemented immutability."
- **Test 7 catches generic `Exception`.** `tests/test_runtime_core.py:183-186` uses `pytest.raises(Exception)`. The intended exception is `dataclasses.FrozenInstanceError`; catching `Exception` would also pass on an unrelated `AttributeError` from a future refactor that breaks the dataclass entirely. Tighten to the specific class.
- **`_REGISTRY` direct import in tests.** `tests/test_runtime_core.py:32` imports `_REGISTRY` from `hassaleh.runtime.core`. This is the only consumer that needs that access; it is the entire reason `_REGISTRY` got promoted into `__all__`. A `reset_registry_for_tests()` helper would let `__all__` shed the underscore-named symbol (see §2 finding).
- **Test 5 (canonical order) is weak.** It only proves "validate runs at all before cap_check"; a stronger assertion is that `session_factory.assert_not_called()` *and* the registered handler's `requires_capability` was never read — currently inferred only from "no `capability-denied` was returned." Acceptable as-is for Track A but worth noting if Track D adds telemetry that re-orders these phases.
- **No test that the handler receives the same `tx` returned by `begin_transaction()`.** Add: capture the `tx` argument inside a recording handler and assert it `is` `_tx(session_factory)`. One line, closes the §2.4 single-tx invariant against drift.

## 6. VERDICT

**CHANGES-REQUESTED**

Track A is on the right shape — the canonical execution order is honoured, the registry-based capability lookup correctly closes I-CR-3, and the dispatch loop is concise and readable. But three load-bearing claims in the implementation log are *documented* without being *implemented*:

1. **§2.4 runtime-bound `now`** — `Ctx.now` is caller-supplied, not runtime-bound. (Blocking; §4)
2. **"Runtime never re-raises"** — commit/rollback/session-open exceptions escape as raw Python exceptions. (Blocking; §4)
3. **`Principal.scopes` immutability** — `frozen=True` does not freeze the underlying `list`; scopes can be elevated post-construction. (Blocking; §2)

Each of these has a small, surgical fix and a test that would have caught it. Track A should land a follow-up commit addressing the three before Track B's first handler is wired in — Track B will assume `ctx.now` is runtime-bound (it appears in every §3 Cypher mutation as `$now`), and Track C/D will assume `Principal.scopes` cannot mutate beneath them.

Non-blocking items (`_REGISTRY` in `__all__`, `Any`-typed handler/session, `Result.error_message` exception leak, missing `requires_capability` validation, weak test 5, generic `Exception` in test 7) are acceptable to defer to Track F's hardening pass — but the `Result.error_message` leak should be tagged in `docs/sprint-13-track-a-implement.md` as a precondition for Track E so it isn't relitigated under time pressure.
